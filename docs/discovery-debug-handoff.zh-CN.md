## 证据与假设

- 最新源码在隔离 Linux/Qt5 环境中 **60/60** 测试通过。这不验证 BB10 实际 UDP 发包或电脑的组播接收。
- 按文档中的 `192.168.3.124/24` 拓扑，当前队列生成 **88 个目标**，`.161` 排在第 **74** 位。代码注释写的最多 80 个，并没有约束此前的邻居和常用地址阶段。
- 对实际最新 `pumpScanQueue()` 注入只会按配置超时的模拟回复，`.161` 在 **3,701 ms** 发起探测，全部 88 个在 **4,901 ms** 完成，没有访问局域网。这不证明真机时序，但队列顺序和 600 ms 超时本身不足以解释为什么 `.161` 在 8 秒期限前没被探测。
- `docs/session-handoff.md` 已将 QNX 6.5、约 8–9 KiB 发送缓冲区以及第 30 包附近 ENOBUFS 写成根因。评审源码与入库材料没有提供相应系统/socket 测量、发送失败返回值或抓包。缓冲区或 ARP 压力是合理假设，尚未证实。
- 当前代码忽略所有 UDP 发送返回值、组播加入结果以及 discovery 启动返回值。`UDP announcement sent` 只证明代码分支执行过。为扫描选择主接口，不等于为组播 socket 选择出站接口。
- 电脑重启会重建 socket 并触发发现；它可能通过公告，也可能通过 register 请求让手机发现自己。仅凭重启成功，不能区分成功路径与此前失败环节。

## 首个交付：一个诊断提交

先保留通常行为，补齐定点诊断，再决定是否调整缓冲区、重试次数或并发数。必要时增加仅限开发的控制，暂停子网扫描并分别执行下面的单目标实验。不要把诊断控制加入日常产品流程。

用英文记录以下事件，包含时间戳和本地 scan/request 标识；不要给 LocalSend JSON 添加诊断字段：

| 环节 | 必须记录 |
| --- | --- |
| 启动 | 源码提交、构建时间、实际 Qt/QNX 版本、运行版本、所选接口/IP/掩码、HTTP 监听端口、UDP bind/join 结果 |
| UDP 发送 | 触发来源（启动/Scan/heartbeat/sweep/manual）、目标、预期接口、队列序号、数据长度、`writeDatagram` 返回值；失败时记录 socket 错误码和消息 |
| UDP 接收 | 来源地址/端口、解码结果或拒绝原因、announce 标志、fingerprint、对端协议与 TCP 端口 |
| HTTP register | 收到请求或主动发起、触发来源、目标端点、耗时、HTTP 状态/网络错误、解码结果 |
| 主机存储 | 按 fingerprint 记录更新/删除、端点和原因，以及更新后的 fingerprint 列表与数量 |
| UI | 模型 revision/数量、成功创建并添加的卡片数量 |
| 扫描结束 | 耗时、已发起/剩余请求、正常结束还是整体超时取消 |

若要验证缓冲区假设，在 BB10 socket 上用 `getsockopt` 读取真实 `SO_SNDBUF`。条件允许时，在失败操作处获取原生错误；不能从普通超时推断 ENOBUFS 或系统版本。UDP 发送成功返回，只表示本机 API 接收了数据，不表示电脑收到。

## 对照实验

使用现有两台电脑、同一局域网，保持防火墙与路由器设置一致。记录每台电脑实际 LocalSend 版本及加密开关。文档中的 `.161` 已关闭加密，先验证该 HTTP 基线。同步时钟或记录明确操作标记。发现抓包期间不传文件。

在受影响电脑上确认实际局域网抓包接口：Fedora 用 `ip route get 192.168.3.124`，macOS 用 `route -n get 192.168.3.124`。然后执行：

```bash
DISCOVERY_EVIDENCE_DIR="$(mktemp -d /tmp/localsend-discovery.XXXXXX)"
PC_CAPTURE_IFACE="replace-with-actual-LAN-interface"
sudo tcpdump -ni "$PC_CAPTURE_IFACE" -s 0 \
    -w "$DISCOVERY_EVIDENCE_DIR/pc-discovery.pcap" \
    'udp port 53317 or tcp port 53317'
```

任一设备使用非默认端口时修改过滤条件。抓包、BB10 诊断日志和电脑 LocalSend 日志一起保留。记录 BAR 哈希并核对运行时构建身份，确认实际部署的产物。已有多个 Build 6 哈希，仅看版本标签不足以确认。

1. **原始失败，再重启电脑：** 两台电脑的客户端先保持运行，再启动 BB10。记录前 10 秒，以及 Scan 可用后的一次正常扫描；若 Scan 被禁用，也记录下来。第二台未出现时，在同一次抓包中只重启该电脑的 LocalSend，并标记时间。确定手机添加它的首个事件。先保存这个基线，再做会改变主机状态的手动注册。
2. **仅 HTTP 的单目标对照：** 另起一轮，电脑持续运行，暂停扫描和 UDP 控制，由 BB10 向受影响 IP 的实际 TCP 端口只发一次 HTTP `/register`。要求 200、有效解码及预期 fingerprint。现在的 `registerPeer()` 同时发送 UDP 和 HTTP，成功不能证明究竟哪条路径工作；不能把现有混合操作当作 HTTP 单独测试。
3. **仅 UDP 的单目标对照：** 另起一轮，暂停 HTTP 扫描，只向受影响电脑的发现端口发送有效 `announce:true` UDP。先试少量定时发送，例如 0、250、1,000 ms，不夹杂 88 台突发。记录每次返回值、电脑是否收到、是否向 BB10 发起 `/register`。UDP 端口按电脑配置确认，公告中的 TCP 端口本身不能证明 UDP 端口。
4. **突发与限速对照：** 若单目标能成功，用相同目标和抓包条件对比现有扫描与限速扫描。比较尝试、本机接受、电脑实际收到的包，以及 HTTP 回调，重点看 `.161`。重复多轮；缓存预热后一次成功不足以证实修复。

## 按证据选择最小修复

| 首个断点 | 下一步 |
| --- | --- |
| 目标根本没进入队列 | 修正地址/接口/范围或排除条件，并记录实际数量上限。没被调度的目标不需要调 socket。 |
| 突发发送失败，单目标成功 | 用有界 QTimer 队列限速，针对已证实的瞬时错误有限重试。取消/停止要清空发送队列和定时器；真机复测缓冲区/ARP 压力。 |
| 本机接受 UDP，电脑没收到 | 检查实际路由/接口及交付情况，包括 ARP、网络过滤；对比单播与组播抓包。仅增大缓冲区没有充分依据。 |
| 电脑收到有效公告，却没发 register | 查电脑发现日志、监听/服务状态和网络设置，不继续修改 BB10 UI。 |
| 电脑发了 register，BB10 没收到 | 检查目标 IP/端口、HTTP 监听和入站链路；区分 TCP 失败与解码拒绝。 |
| BB10 接受 register，主机随后消失 | 查删除事件与未完成请求。避免一次旧注册请求失败就删除刚被确认的主机。 |
| 主机存储和模型都有两项，界面只有一张 | 根据实际创建/添加数，返回原生卡片或布局排查。 |
| 只有真机上的 `.161` 发起得很晚 | 测量实际定时器、事件循环延迟和在途请求寿命，再调整并发或期限。 |

若证实突发失败，可以从每 20 ms 的 timer tick 发送 1–2 包、每目标最多尝试三次并设置整体预算开始实验。这些是实验参数，不是已证实的 QNX 极限。期限须覆盖排队重试并允许应答到达，不要不分错误原因地全部重试。已成功发现的端点可记忆并优先复查，但不能把记忆或手动目标当作首次发现通过的证据。

若路由证据指向组播出站接口错误，用 Qt4 支持的 `setMulticastInterface` 明确指定；扫描和状态使用同一 LAN 信息。检查 bind/join/write 失败，区分发现降级与 HTTP 核心可用。保持 HTTP-only MVP 传输策略明确；HTTPS 仅发现是另一个用例。新增 HTTPS 探测和忽略证书错误不能替代明文基线的验证。

## 真机验收与 agy 回报格式

做完定点修复后，两台电脑先保持运行，至少执行 10 次 BB10 冷启动和 10 次可用的 Scan。不得重启电脑客户端或手动预热缺失主机；再测试受影响电脑后来加入。固定测试局域网内，两台都须在约定 10 秒内出现，按 fingerprint 保持两台、显示两张卡片，并实际向第二台 HTTP 主机发送。记录启动/Scan 漏检数、每个 fingerprint 的出现时间、短暂出现又被删除的情况。这是有限的可复现验收，不是对所有网络的保证。

提交回报须包含：源码提交和 BAR/运行身份；修复前失败抓包；首个失败环节；对应的最小修复；前后真机轮次结果；覆盖修复行为的主机检查；未解决限制。此场景通过前，R018/R019 保持开放。主机测试数量通过或靠电脑重启成功，不能关闭该问题。
