# Fedora Development & Validation Summary

English | [Simplified Chinese](fedora-development-summary.zh-CN.md)

This document provides a comprehensive record of the development, containerization, debugging, and verification work conducted on the Fedora development workstation for the `localsend-bb10` project targeting BlackBerry Passport (BB10 OS 10.3.x).

---

## 1. Containerized BB10 Toolchain (`docker/bb10-toolchain`)

### 1.1 Problem & Challenge
The BlackBerry 10 Native SDK (NDK 10.3.1.995) was released around 2014 and relies heavily on 32-bit x86 binaries (`ntoarm-gcc`, `ntoarm-ld`, `qcc`, and a 32-bit Java runtime for `blackberry-nativepackager`). Modern 64-bit Linux distributions (such as Fedora 40+) have migrated to glibc 2.39+, dropped legacy 32-bit dependencies, and exhibit incompatibilities with the NDK's bundled Python and packaging tools.

### 1.2 Architecture & Design Decisions
To ensure a fully reproducible and portable build environment without hardcoding proprietary BlackBerry binaries into git:
- **Clean Container Base**: Built on `debian:bookworm-slim` with `i386` multiarch enabled (`libc6:i386`, `libstdc++6:i386`, `zlib1g:i386`, `openjdk-17-jre-headless`).
- **External NDK Mounting**: The NDK is mounted at runtime via `-v ${HOME}/bbndk:/bbndk:z`, keeping the Docker image license-compliant and compact (~765 MB).
- **Makefile Sanitizer (`sanitize-makefile.py`)**: Automatically strips unsupported host flags generated by legacy `qmake` specs before invocation by `ntoarm-gcc`.
- **Reusable CLI Wrapper (`bb10-build`)**: Created a standardized build runner in `docker/bb10-toolchain/bin/bb10-build` and `scripts/build-bb10.sh` that compiles the ARMv7le ELF binary, strips debug symbols, and bundles the signed `.bar` package. Future BB10 Cascades applications can reuse this container directly.

## 2. Issues Identified and Resolved (R012 – R018)

During real-device deployment and testing on the physical BlackBerry Passport (`192.168.3.124`), the following critical issues were identified and resolved:

| ID | Issue & Symptom | Root Cause | Resolution |
| :--- | :--- | :--- | :--- |
| **R012** | Application packaging crash on launch | `bar-descriptor.xml` lacked Cascades shared library specification and entry point linkage. | Configured `localsend-bb10.so` entry asset with `entryPointType` set to `Qnx/Cascades` and dynamic entry point `localsend-bb10`. |
| **R013** | Wi-Fi device deployment friction | Manual deployment via command line was error-prone. | Created `scripts/deploy-bb10.sh` supporting automated packaging, Wi-Fi deployment, and launch via `blackberry-deploy`. |
| **R014** | QML crash on launch (desktop return) | Cascades QML engine lacks the `Connections` element. Parsing failed, causing `createRootObject()` to return `NULL`. | Replaced `Connections` with native Cascades property bindings (`property variant peerList: app.peers` with `onPeerListChanged`). Added diagnostics in `main.cpp`. |
| **R015** | Received files inaccessible | Files were saved into the application sandbox (`data/received`), which is hidden from the BB10 File Manager. | Changed default save path to `/accounts/1000/shared/downloads/` with automatic directory creation and `access_shared` permission. |
| **R016** | Peer discovery failure / slow search | UDP multicast packets (`224.0.0.167`) were intermittently dropped by Wi-Fi routers; lack of periodic announcement. | Added limited broadcast (`255.255.255.255:53317`), dynamic subnet directed broadcast, and a 30-second background heartbeat timer (`m_announceTimer`). |
| **R017** | Missing Scan/Refresh button & UI clutter | Cascades `TabbedPane.showTabsOnActionBar` occupies all bottom action slots, hiding page actions in overflow. Duplicate inline scan buttons existed. | Unified scanning into the top-right `TitleBar.acceptAction` (`Scan`), matching the official LocalSend client design and ensuring permanent visibility. |
| **R018** | Peer list stale entries | Devices leaving the network remained in the peer list indefinitely. | Implemented full-effect scan: prunes peers older than 120s, rejoins multicast groups, resets heartbeat, and actively probes reachable peers via HTTP. |

## 3. Automated Interoperability Testing (`tests/interoperability.py`)

A comprehensive Python test suite was developed and executed on the Fedora host to validate protocol compliance against official LocalSend clients:
- **Test Fixture Generation**: Created deterministic binary fixtures (`0b.bin`, `1k.bin`, `10m.bin`), special-character filename fixture (`notes with spaces.txt`), and UTF-8 Chinese filename fixture (`测试文件_照片.png`), with SHA-256 manifest generation.
- **HTTP Endpoint Verification**: Validated `/api/localsend/v2/info`, `/api/localsend/v2/register`, `/api/localsend/v2/prepare-upload`, and `/api/localsend/v2/upload` against local official LocalSend (`v1.18.2`). All 4 endpoints passed.
- **Bidirectional Streaming Transfer**: Verified chunked streaming upload, backpressure handling, and SHA-256 digest matching between the mock peer and target receiver.

## 4. Code Review & Codex Integration Security Assessment

When preparing for code review by external agents or LLM services (such as OpenAI Codex), two architectural paths were analyzed:

### Path A: Direct Local Machine Access (Rejected)
*Granting remote SSH, agent bridge, or shell access into the local Fedora development machine.*
- **Security Risks**:
  - **Violation of Least Privilege**: Grants execution access to local development environment, user home directory, and local network.
  - **Credential Exposure**: Exposes BlackBerry signing keys (`author.p12`), device deployment passwords, SSH private keys, and local network topologies.
  - **Non-auditability**: Command execution histories and mutations on the host are difficult to audit or rollback cleanly.

### Path B: Git Remote Branch & Pull Request Review (Adopted)
*Pushing isolated commits to a dedicated Git branch on GitHub (`feature/bb10-discovery-ui-review`) and conducting code review via repository diffs / PR.*
- **Security Advantages**:
  - **Zero Credential Exposure**: No credentials, private keys, or internal network endpoints leave the development machine.
  - **Explicit Review Scope**: The reviewer inspects only committed code diffs against `master`.
  - **Immutable Audit Trail**: All feedback and code suggestions are tracked through standard Git PR workflows.
